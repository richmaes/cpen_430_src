# Architecture: RGMII + MDIO Ethernet MAC with a Peek/Poke Control State Machine

**Target board:** Terasic DE2-115 (Cyclone IV E, EP4CE115F29C7)
**PHY:** Marvell 88E1111 (ENET0 and/or ENET1), RGMII mode selected via jumper JP1/JP2 (pins 1-2 shorted)
**Status:** Draft for review — assumptions that need your confirmation are called out explicitly in
[§9](#9-open-assumptions-to-confirm) and inline as `> ASSUMPTION:` notes.

## 1. Goals

1. **PHY interface = RGMII** (not MII). Jumpers are already set to RGMII on the board.
2. **MDIO management interface enabled** so the FPGA can read/write Marvell 88E1111 PHY registers
   (link status, speed/duplex, HWCFG, reset, loopback/test modes, etc.) instead of relying solely on
   PHY hardware-config straps.
3. Use the DE2-115 manual's **Web Server Demonstration** (§6.12, manual pages 108-118) as the
   conceptual starting point for the MAC/PHY wiring and MDIO setup — **but with no Nios II / NicheStack /
   MicroC/OS-II / SGDMA software stack**. All register access is done by a small hardware
   **peek-and-poke state machine** instead of a soft CPU.
4. End state is a hardware-only bring-up/debug path: configure the PHY over MDIO, confirm RGMII link
   up at the negotiated speed, and exercise the existing MAC-bypass loopback path
   ([eth_core.sv](/c:/Users/maes/src/cpen_430_src/mac_byp_demo/eth_core.sv)) — all without any
   embedded software.

## 5. RGMII PHY interface

- Mode select: jumper JP1 (ENET0) / JP2 (ENET1), **pins 1-2 shorted = RGMII** (already done per your
  note).
- `tse_mac`'s `mac_rgmii_connection` interface (`rgmii_in[3:0]`, `rgmii_out[3:0]`, `rx_control`,
  `tx_control`) is the DDR-encoded, pin-level RGMII bus — the IP's generated hierarchy already includes
  the DDR SERDES logic for this (`altera_tse_rgmii_in4.v` / `altera_tse_rgmii_out4.v` /
  `altera_tse_rgmii_module.v` under `ip/tse_mac/`), so **no extra `ALTDDIO_IN`/`ALTDDIO_OUT` primitives
  need to be instantiated by hand** — these ports connect essentially directly to the board's
  `ENET0_RX_DATA[3:0]`/`ENET0_RX_DV`/`ENET0_RX_ER` and `ENET0_TX_DATA[3:0]`/`ENET0_TX_EN`/`ENET0_TX_ER`
  pins (the same physical pins used for MII — RGMII just reinterprets them as a DDR bus).
- `ENET0_RX_CLK` → `tse_mac.rx_clk`/`ff_rx_clk` (RXC from PHY).
- `ENET0_GTX_CLK` → must become the RGMII **TXC** output driven by the FPGA (see clocking, §6) instead of
  being tied to `1'b0` as it is today.
- `ENET0_TX_CLK` (an *input* in MII mode) is not used by RGMII and can be left unconnected.

> ASSUMPTION: exact `rgmii_in`/`rgmii_out`/`rx_control`/`tx_control` ↔ board-pin mapping should be

> interface-signal chapter before finalizing pin assignments in the `.qsf`. This document captures

## 6. Clocking for RGMII

RGMII requires the MAC side to drive the transmit clock (TXC) at the **negotiated link rate** — 125 MHz
(1000 Mbps), 25 MHz (100 Mbps), or 2.5 MHz (10 Mbps) — and to receive RXC from the PHY at the same rate.
`tse_mac` exposes `eth_mode` and `ena_10` as status outputs that indicate the current negotiated mode;
these must drive a clock-select mux feeding `ENET0_GTX_CLK`.

Needed new logic (does not exist in the current design):
1. An **ALTPLL** sourced from `ENETCLK_25` (the board's dedicated 25 MHz Ethernet reference clock) or
   `CLOCK_50`, generating 125 MHz, 25 MHz, and 2.5 MHz clock candidates.
2. A clock mux (candidate: reuse/adapt `altera_tse_clk_cntl.v`, already present under
   `ip/tse_mac/` as a related IP file) that selects among those three based on `eth_mode`/`ena_10` and
   drives `ENET0_GTX_CLK` (TXC) and `tse_mac.tx_clk`/`ff_tx_clk`.

> ASSUMPTION: this clock-mux block is new RTL that still needs to be written/instantiated; it's flagged
> here as a required piece of the architecture but is not yet implemented anywhere in the repo.

## 7. MDIO management interface

- Pins: `ENET0_MDC` (output) / `ENET0_MDIO` (bidirectional), 2.5V I/O, already present on the top-level
  port list in `DE2_115.sv` (currently tied off — to be connected to `tse_mac.mdc` /
  `tse_mac.mdio_in`/`mdio_out`/`mdio_oen`).
- `tse_mac` was generated with `useMDIO = true` and `mdio_clk_div = 40`. The reference Web Server demo
  assumes a 100 MHz control-port clock (`clk`) to get a 2.5 MHz MDC (100 MHz / 40). This design's control
  port runs off `CLOCK_50` (50 MHz) per the existing `DE2_115.sv`, so with the same divisor MDC comes out
  at **1.25 MHz** — still within the 88E1111's spec (MDC max 2.5 MHz), just slower. No change needed
  unless a faster MDIO turnaround is desired.
- PHY address straps: ENET0 = `10000` (0x10), ENET1 = `10001` (0x11) (Table 4-20/22 in the manual).
- MDIO access is memory-mapped through the MAC's own Avalon-MM control port (no separate MDIO bus
  master needed): `mdio_addr0`/`mdio_addr1` control-port registers select which PHY address MDIO Space 0
  / Space 1 target, then dword offsets `0x80-0x9F` (Space 0) and `0xA0-0xBF` (Space 1) map directly to
  PHY registers 0-31 — a read or write to one of these offsets triggers a full MDIO frame on the wire.

## 8. Replacing Nios II with a peek/poke state machine

The manual's Web Server Demo uses Nios II + NicheStack + a web UI to let a user inspect/change MAC and
PHY registers (link status, speed, statistics, etc.) at run time. We have no soft CPU, so that
interactive register access is replaced by a small FSM that is the **sole Avalon-MM master** on
`tse_mac`'s control port, driven directly from DE2-115 switches/keys and reporting results on the HEX
displays/LEDs — a hardware equivalent of a software "peek/poke" debug console.

### 8.1 Proposed FSM interface (new module, e.g. `peek_poke_ctrl.sv`)

| Signal | Direction | Purpose |
|---|---|---|
| `SW[7:0]` | in | 8-bit control-port dword address (`reg_addr`) — covers MAC config regs and both MDIO spaces (`0x80-0xBF`) |
| `SW[16]` | in | load/shift strobe source select or data-half select (low/high 16 bits) — see note below |
| `SW[15:0]` (reused) | in | 16-bit data half, loaded into an internal 32-bit write-data shift register across two key presses |
| `KEY[1]` | in | **Load**: latch `SW[7:0]` as `reg_addr`, and `SW[15:0]` into the selected half of the write-data register |
| `KEY[2]` | in | **Poke** (write): drive `reg_data_in`/`reg_wr` for one control-port write cycle, wait for `~reg_busy` |
| `KEY[3]` | in | **Peek** (read): drive `reg_rd` for one control-port read cycle, wait for `~reg_busy`, latch `reg_data_out` |
| `HEX0-3` | out | last `reg_data_out` (or pending write data), hex digits |
| `HEX4-5` | out | last `reg_addr` |
| `LEDG[0]` | out | FSM busy / `reg_busy` passthrough |
| `LEDR` | out | optional: live PHY status bits (link/speed/duplex) continuously peeked from the MDIO-mapped PHY register 17 (Copper Specific Status 1) or register 1 (BMSR) |

### 8.2 FSM states

```
IDLE → LOAD_ADDR_DATA (on KEY[1]) → IDLE
IDLE → WRITE (on KEY[2]) → WAIT_BUSY → IDLE     (reg_wr=1 until reg_busy deasserts)
IDLE → READ  (on KEY[3]) → WAIT_BUSY → LATCH → IDLE
```

This is intentionally minimal — one address register, one 32-bit data register, one Avalon-MM
read/write cycle per key press, debounced on `KEY`.

### 8.3 Typical PHY bring-up sequence performed manually with this interface

1. Set `mdio_addr0 = 0x10` (ENET0 PHY address) via one poke.
2. Peek PHY register 2/3 (`PHYID1`/`PHYID2`, at offsets `0x82`/`0x83`) to confirm the 88E1111 responds
   over MDIO.
3. Peek PHY register 1 (BMSR, offset `0x81`) to confirm link-up / auto-negotiation complete.
4. Peek PHY register 17 (Copper Specific Status 1, offset `0x91`) for negotiated speed/duplex, and
   compare against `tse_mac.eth_mode`/`ena_10`.
5. Poke MAC `command_config` register to enable TX/RX as needed for the `eth_core` loopback to pass
   traffic.

> you specified — please confirm or adjust (e.g., you may prefer a UART-based peek/poke console instead

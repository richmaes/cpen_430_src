## 1. About This IP Core

The Intel® FPGA Triple-Speed Ethernet IP core is a configurable intellectual property (IP) core that complies with the IEEE 802.3 standard.

It incorporates a 10/100/1000-Mbps Ethernet media access controller (MAC) and an optional 1000BASE-X/SGMII physical coding sublayer (PCS) with an embedded PMA built with either on-chip transceiver I/Os or LVDS I/Os. When offered in MAC-only mode, the IP connects with an external PHY chip using MII, GMII, or RGMII interface.

The IP core was tested and successfully validated by the University of New Hampshire (UNH) interoperability lab.

### 1.2. Features

- Complete triple-speed Ethernet IP: 10/100/1000-Mbps Ethernet MAC, 1000BASE-X/SGMII PCS, and embedded PMA.
- Successful validation from the University of New Hampshire (UNH) InterOperability Lab.
- 10/100/1000-Mbps Ethernet MAC features:
  - Multiple variations: 10/100/1000-Mbps Ethernet MAC in full duplex, 10/100-Mbps Ethernet MAC in half duplex, 10/100-Mbps or 1000-Mbps small MAC (resource-efficient variant), and multiport MAC that supports up to 24 ports.
  - Support for basic, VLAN, stacked VLAN, and jumbo Ethernet frames. Also supports control frames including pause frames.
  - Optional internal FIFO buffers, depth from 64 bytes to 256 Kbytes.
  - Optional statistics counters.
- MAC interfaces:
  - Client side—8-bit or 32-bit Avalon® Streaming (Avalon-ST)
  - Network side—medium independent interface (MII), gigabit medium independent interface (GMII), or reduced gigabit medium independent interface (RGMII) on the network side. Optional loopback on these interfaces.
  - Optional management data I/O (MDIO) master interface for PHY device management.
- 1000BASE-X/SGMII PCS features:
  - Compliance with Clause 36 of the IEEE standard 802.3.
  - Optional embedded PMA implemented with serial transceiver or LVDS I/O and soft CDR in Intel FPGA devices that support this interface at 1.25-Gbps data rate.
  - Support for auto-negotiation as defined in Clause 37.
  - Support for connection to 1000BASE-X PHYs. Support for 10BASE-T, 100BASE-T, and 1000BASE-T PHYs if the PHYs support SGMII.
- PCS interfaces:
  - Client side—MII or GMII
  - Network side—ten-bit interface (TBI) for PCS without PMA; 1.25-Gbps serial interface for PCS with PMA implemented with serial transceiver or LVDS I/O and soft CDR in Intel FPGA devices that support this interface at 1.25-Gbps data rate.
- Programmable features via 32-bit configuration registers:
  - FIFO buffer thresholds.
  - Pause quanta for flow control.
  - Source and destination MAC addresses.
  - Address filtering on receive, up to 5 unicast and 64 multicast MAC addresses.
  - Promiscuous mode—receive frame filtering is disabled in this mode.
  - Frame length—in MAC only variation, up to 64 Kbytes including jumbo frames. In all variants containing 1000BASE-X/SGMII PCS (with or without MAC), the frame length is up to 10 Kbytes.
  - Optional auto-negotiation for the 1000BASE-X/SGMII PCS.
- Error correction code protection feature for internal memory blocks.
- Optional IEEE 1588v2 feature for 10/100/1000-Mbps Ethernet MAC with SGMII PCS and embedded serial PMA variation operating without internal FIFO buffer in full-duplex mode, 10/100/1000-Mbps MAC with SGMII PCS and embedded LVDS I/O, or MAC only variation operating without internal FIFO buffer in full-duplex mode. These features are supported in Intel Stratix 10, Arria V, Intel Arria 10, Intel Cyclone 10 GX, Cyclone V, Intel MAX 10, and Stratix V device families.

### 1.3. 10/100/1000 Ethernet MAC Versus Small MAC

**Table 3. Feature Comparison between 10/100/1000 Ethernet MAC and Small MAC**

| Feature | 10/100/1000 Ethernet MAC | Small MAC |
|---|---|---|
| Speed | Triple speed (10/100/1000 Mbps) | 10/100 Mbps or 1000 Mbps |
| External interfaces | MII/GMII or RGMII | MII only for 10/100 Mbps small MAC, GMII or RGMII for 1000 Mbps small MAC |
| Control interface registers | Fully programmable | Limited programmable options. The following options are fixed: Maximum frame length is fixed to 1518 (jumbo frames not supported); FIFO buffer thresholds are set to fixed values; Store and forward option is not available; Interpacket gap is set to 12; Flow control is not supported (pause quanta is not in use); Checking of payload length is disabled; Supplementary MAC addresses are disabled; Padding removal is disabled; Sleep mode and magic packet detection is not supported. |
| Synthesis options | Fully configurable | Limited configurable options. The following options are NOT available: Flow control; VLAN; Statistics counters; Multicast hash table; Loopback; TBI and 1.25 Gbps serial interface; 8-bit wide FIFO buffers |

### 1.5. Example Applications

This section shows example applications of different variations of the Triple-Speed Ethernet IP core. The 10/100/1000-Gbps Ethernet MAC only variation can serve as a bridge between the user application and standard fast or gigabit Ethernet PHY devices.

- **Figure 5/6.** Stand-Alone 10/100/1000 Mbps Ethernet MAC — Intel FPGA device containing a Triple-Speed Ethernet IP Core (10/100/1000-Mbps Ethernet MAC) connects via Avalon-ST to a User Application and via Avalon-MM to a Management Application; on the network side it connects via MII/GMII/RGMII and MDIO to an external Gigabit or Fast Ethernet PHY Device, which connects to copper.

When configured to include the 1000BASE-X/SGMII PCS function, the IP core can seamlessly connect to any industry standard gigabit Ethernet PHY device via a TBI. Alternatively, when the 1000BASE-X/SGMII PCS function is configured to include an embedded PMA, the IP core can connect directly to a gigabit interface converter (GBIC), small form-factor pluggable (SFP) module, or an SGMII PHY.

### 1.6. IP Core Verification

For each release, Intel verifies the Triple-Speed Ethernet IP core through extensive simulation and internal hardware verification in various Intel FPGA device families. The University of New Hampshire (UNH) InterOperability Lab also successfully verified the IP core prior to its release.

Intel used a highly parameterizeable transaction-based testbench to test the following aspects of the IP core:
- Register access
- MDIO access
- Frame transmission and error handling
- Frame reception and error handling
- Ethernet frame MAC address filtering
- Flow control
- Retransmission in half-duplex

Intel has also validated the Triple-Speed Ethernet IP core in both optical and copper platforms using the following development kits:
- Nios® II Development Kit, Cyclone II Edition (2C35)
- Intel Arria 10 FPGA Development Kit
- Intel Cyclone 10 LP FPGA Development Kit
- Stratix III FPGA Development Kit
- Stratix IV FPGA Development Kit
- Stratix V FPGA Development Kit
- Intel Stratix 10 FPGA Development Kit
- Quad 10/100/1000 Marvell PHY
- MorethanIP 10/100 and 10/100/1000 Ethernet PHY Daughtercards

#### 1.6.1. Optical Platform

In the optical platform, the 10/100/1000 Mbps Ethernet MAC, 1000BASE-X/SGMII PCS, and PMA functions are instantiated.

The FPGA application implements the Ethernet MAC, the 1000BASE-X PCS, and an internal system using Ethernet connectivity. This internal system retrieves all frames received by the MAC function and returns them to the sender by manipulating the MAC address fields, thus implementing a loopback. A direct connection to an optical module is provided through an external SFP optical module. Certified 1.25 GBaud optical SFP transceivers are Finisar 1000BASE-SX FTLF8519P2BNL, Finisar 1000BASE-LX FTRJ-1319-3, and Avago Technologies AFBR-5710Z.

#### 1.6.2. Copper Platform

In the copper platform, Intel FPGA tested the Triple-Speed Ethernet IP core with an external 1000BASE-T PHY devices. The IP core is connected to the external PHY device using MII, GMII, RGMII, and SGMII, in conjunction with the 1000BASE-X/SGMII PCS and PMA functions.

A 10/100/1000 Mbps Ethernet MAC and an internal system are implemented in the FPGA. The internal system retrieves all frames received by the MAC function and returns them to the sender by manipulating the MAC address fields, thus implementing a loopback. A direct connection to an Ethernet link is provided through a combined MII to an external PHY module. Certified 1.25 GBaud copper SFP transceivers are Finisar FCMJ-8521-3, Methode DM7041, and Avago Technologies ABCU-5700RZ.

## 2. Getting Started with Intel FPGA IP Cores

Intel FPGA IP cores are the building blocks of your design. You can use the Intel Quartus Prime IP Catalog to select, customize, and generate files representing your custom IP variation.

### 2.1. IP Catalog and Parameter Editor

The IP Catalog (**Tools** ➤ **IP Catalog**) and parameter editor help you search and customize IP cores. You can quickly find and launch IP with design-specific parameter options. After you generate the customized IP variation, the parameter editor presents a summary of the generated files.

You use individual IP core variation files (**.ip**) in your project, instantiating them in your design. You can also use IP integration tools like Platform Designer to integrate your IP into a larger system.

#### 2.1.1. Launching the IP Parameter Editor to Instantiate or Edit IP

Use the New IP Variant window to locate the IP you want to instantiate, specify a name, and choose a target device for the variation. Use the parameter editor to specify parameters, generate output file options, and preview the generated files for a particular IP core variation.

### 2.2. Specifying IP Core Parameters and Options

Follow these steps to specify IP core options and parameters in the parameter editor:

1. Specify parameters that define the IP core functionality, port configurations, and device-specific features.
2. Specify options for processing the IP core files in other EDA tools.
3. Click **Generate HDL** to generate the IP core.

### 2.3. IP Core Generation Output (Intel Quartus Prime Pro Edition)

The Intel Quartus Prime software generates the following output file structure for IP cores, including `<your_ip>.ip` design files, synthesis and simulation files for third-party EDA tools, example testbench files (if available), and Compile Point synthesis files.

### 2.4. Simulating Intel FPGA IP Cores

The Intel Quartus Prime software supports IP core RTL simulation in specific EDA simulators, generating simulation model files and simulation script files during IP generation.

### 2.5. Instantiating Multiple Instances of Triple-Speed Ethernet IP Cores

When you instantiate multiple instances of the Triple-Speed Ethernet IP core with the SGMII or 1000BASE-X PCS and embedded PMA function configured to use PLL and clock resources, you must share the `reconfig_to_xcvr` and `reconfig_from_xcvr` ports across all instances to ensure correct dynamic reconfiguration of the shared PLL.

### 2.6. Upgrading Your IP Cores

When you update to the latest version of the Intel Quartus Prime software, or point your current project to a newer version of an IP variant, you may need to regenerate your IP core to include enhancements and ensure compatibility.

**Related Information:** Upgrading IP Cores — provides general information on IP core versions and upgrading, applicable across Intel FPGA IP.

## 4. Functional Description

This chapter describes the functions of the 10/100/1000-Mbps Ethernet MAC, 1000BASE-X/SGMII PCS, and the optional embedded PMA, as well as how these blocks interact with each other and with the client logic.

### 4.1. 10/100/1000 Ethernet MAC Architecture

The 10/100/1000-Mbps Ethernet MAC implements a standard IEEE 802.3 media access control function. It consists of a transmit datapath, a receive datapath, address filtering logic, flow control logic, optional statistics counters, and an Avalon-MM configuration and status register interface.

*Figure 9. MAC Architecture Block Diagram* — shows the Avalon-ST transmit client interface feeding a Tx FIFO and Tx MAC logic block, which outputs to the MII/GMII/RGMII Tx interface; symmetrically, the Rx MII/GMII/RGMII interface feeds Rx MAC logic, address checking, and an Rx FIFO, which outputs to the Avalon-ST receive client interface. A Control/Status Register block, connected via Avalon-MM, configures both datapaths and optionally an MDIO master interface and statistics counters module.

#### 4.1.1. Transmit Datapath

The transmit datapath accepts frames from the client logic over the Avalon-ST transmit interface, optionally buffers them in the transmit FIFO, inserts the preamble and start-of-frame delimiter (SFD), pads short frames to the minimum frame length (unless padding is disabled), optionally inserts or strips VLAN tags, computes and appends the frame check sequence (FCS) unless the client supplies it, and enforces the minimum interpacket gap (IPG) before presenting the frame to the selected MII/GMII/RGMII network interface.

In store-and-forward mode, the IP core buffers and verifies that an entire valid frame has been received from the client interface before starting transmission on the network side, preventing a FIFO underflow condition from generating a malformed/truncated frame on the wire. In cut-through mode, transmission starts as soon as enough data has accumulated in the FIFO to satisfy the programmed low threshold, minimizing latency at the cost of a small risk of underflow on a misbehaving client.

#### 4.1.2. Receive Datapath

The receive datapath accepts frames from the external PHY through the selected network interface, strips the preamble and SFD, performs address filtering, optionally strips the VLAN tag, checks the FCS, checks frame length against configured minimum/maximum values, and forwards accepted frames to the client logic over the Avalon-ST receive interface together with status information indicating any errors detected (CRC error, length error, alignment error, and so on) via the end-of-packet error signal.

#### 4.1.3. Address Checking

The receive address-checking block filters incoming frames based on destination MAC address. The MAC supports:
- A single primary unicast address.
- Up to four supplementary unicast addresses (when enabled).
- A 64-bit multicast hash table for multicast address filtering.
- A broadcast address pass filter.
- A promiscuous mode that disables all address filtering, passing all received frames (valid and invalid addresses) to the client.

#### 4.1.4. Flow Control

The MAC supports IEEE 802.3 Annex 31B flow control using PAUSE frames. On the transmit side, the MAC can be directed (via a control register or an Avalon-ST in-band flow-control signal) to emit a PAUSE frame with a programmable pause quanta value. On the receive side, the MAC recognizes received PAUSE frames addressed to the reserved multicast control address and, if addressed to this MAC, suspends frame transmission for the duration specified in the pause quanta field of the received frame.

#### 4.1.5. VLAN and Jumbo Frame Support

The MAC supports standard Ethernet frames, IEEE 802.1Q VLAN-tagged frames, stacked (double) VLAN tagged frames, and jumbo frames up to a configurable maximum frame length (up to 64 Kbytes for MAC-only variants; up to 10 Kbytes for variants containing the 1000BASE-X/SGMII PCS).

#### 4.1.6. Magic Packet Detection

When enabled, the MAC can detect "magic packet" frames — frames containing the destination MAC address repeated 16 times, preceded by a synchronization stream of six 0xFF bytes — used to wake the attached system from a low-power sleep state. The magic packet address can be fixed to the station address or made independently programmable.

#### 4.1.7. Statistics Counters

When enabled, the IP core implements a set of IEEE 802.3 RMON-like statistics counters tracking, per direction, items such as: total frames, total bytes (octets), unicast/multicast/broadcast frame counts, undersized and oversized frames, CRC errors, alignment errors, VLAN-tagged frames, control frames and pause frames, and frames in various length-range buckets (64 bytes, 65-127, 128-255, 256-511, 512-1023, 1024-1518, 1519-max). Each counter is a 32-bit (or paired 32-bit) register readable through the Avalon-MM configuration interface, described in detail in the *Configuration Register Space* chapter.

#### 4.1.8. MDIO Master Interface

When enabled, the IP core includes an MDIO master controller that implements the IEEE 802.3 Clause 22 (and, for some configurations, Clause 45) management interface, allowing the Avalon-MM host to read and write registers in an attached external PHY device over the two-wire MDIO/MDC serial bus.

### 4.2. Small MAC Architecture

The 10/100-Mbps and 1000-Mbps Small MAC variations provide a resource-optimized subset of the full MAC's functionality, targeted at applications that do not require full programmability. As summarized in Table 3, several features (jumbo frames, flow control, supplementary addresses, sleep mode, and configurable FIFO thresholds) are either disabled or fixed to default values in the Small MAC to reduce logic utilization.

### 4.3. 1000BASE-X/SGMII PCS Architecture

The 1000BASE-X/SGMII PCS implements the physical coding sublayer functions defined in Clause 36 of IEEE 802.3, performing 8B/10B encoding and decoding, comma detection and word alignment, elastic buffering for clock-domain crossing, and the auto-negotiation state machine defined in Clause 37 (extended, for SGMII, to interoperate with the Cisco-defined SGMII auto-negotiation protocol used between a MAC and a copper PHY).

*Figure 10. 1000BASE-X/SGMII PCS Block Diagram* — shows the GMII/MII client interface connected to an 8B/10B Encoder/Decoder, Auto-Negotiation state machine, Elastic Buffer, and Synchronization state machine, which connects to the TBI (or embedded PMA) on the network side.

#### 4.3.1. 8B/10B Encoding and Decoding

Transmit data received over the client GMII interface is encoded into 10-bit code-groups prior to serialization; received 10-bit code-groups from the network side are decoded back to 8-bit data with running-disparity checking to detect code errors.

#### 4.3.2. Synchronization

A synchronization state machine, as defined in IEEE 802.3 Clause 36, monitors incoming code-groups for valid commas and ordered sets to achieve and maintain word and comma alignment with the remote link partner.

#### 4.3.3. Auto-Negotiation

When auto-negotiation is enabled, the PCS exchanges Config_Reg ordered sets with its link partner to negotiate duplex mode and (for SGMII) link speed, reporting the result through status registers readable by the Avalon-MM host and, when the SGMII bridge is enabled, reflecting the negotiated speed and duplex automatically to the GMII/MII client-side interface clock and signals.

#### 4.3.4. SGMII Bridge

When the SGMII bridge option is enabled, the IP core automatically adapts the client-side GMII/MII interface timing (including a clock-rate adjustment for 10/100-Mbps operation over an inherently gigabit-rate SGMII link) based on the auto-negotiated link speed, so that an attached 10/100/1000-Mbps MAC function does not need to separately track the negotiated SGMII speed.

### 4.4. Embedded PMA

When configured with an embedded PMA, the IP core instantiates either a dedicated high-speed serial transceiver channel (GXB, using the device's native transceiver primitives) or an LVDS SERDES-based soft PMA with a clock data recovery (CDR) circuit, eliminating the need for an external TBI-to-serial converter or using the device's dedicated gigabit transceivers directly for 1.25-Gbps serial connectivity to copper SGMII PHYs or optical SFP/GBIC modules.

#### 4.4.1. Transceiver-Based PMA (GXB)

For device families with dedicated high-speed serial transceivers, the PMA option instantiates a transceiver PHY IP core (configured for 1.25 Gbps, 8B/10B operation) alongside dynamic reconfiguration logic (`reconfig_to_xcvr`/`reconfig_from_xcvr`) to allow runtime adjustment of transceiver analog settings.

#### 4.4.2. LVDS-Based PMA

For device families or board designs where dedicated transceivers are unavailable or undesirable, the PMA option instantiates a soft CDR built from LVDS SERDES I/O primitives and PLL resources, recovering the 1.25-Gbps serial bit stream using device I/O and fabric logic rather than dedicated transceiver blocks.

### 4.5. Reset

The IP core provides separate reset domains for the Avalon-MM control interface clock domain, the Avalon-ST client clock domain, and the network-side (MII/GMII/RGMII/TBI/serial) clock domain, allowing each clock domain to be reset independently where asynchronous or mismatched clocks are in use. Refer to the *Interface Signals* chapter for the full list of reset signals and their relationships to each clock domain.

### 4.6. Clocking

Each variation of the IP core may use several independent clock domains, for example: the Avalon-ST/Avalon-MM client-side clock, the MII/GMII/RGMII network-side clock(s) (which may differ for transmit and receive and may be sourced from the external PHY), and, for PCS/PMA variations, a reference clock used to generate the 1.25-Gbps (or 125-MHz TBI) network-side clock domain. Refer to the *Interface Signals* chapter for clock signal descriptions and the *Timing Constraints* chapter for the applicable constraints (`.sdc`) delivered with the IP core.

### 4.7. IEEE 1588v2 Feature

When enabled (on supported variations and device families only), the IEEE 1588v2 feature timestamps selected transmitted and received Precision Time Protocol (PTP) event frames at the point they cross the MII/GMII boundary, providing hardware timestamp accuracy suitable for implementing the IEEE 1588-2008 (PTPv2) protocol in system software. Timestamps are captured into dedicated registers in the configuration register space (see the *Configuration Register Space* chapter) and are tagged to the corresponding frame using a FIFO-based tag mechanism so that software can correlate a given timestamp with the PTP frame that generated it.

#### 4.7.1. Transmit Timestamping

On the transmit side, the egress timestamp of a PTP event message is captured at the GMII boundary once the start of frame is transmitted, compensating for the fixed pipeline latency through the transmit datapath, and stored together with a frame identifier (snapshot) that software reads back after transmission completes.

#### 4.7.2. Receive Timestamping

On the receive side, the ingress timestamp of a PTP event message is captured at the GMII boundary as the start of frame is received, similarly compensated for receive datapath latency, and made available to software together with the received frame.

#### 4.7.3. Time-of-Day Counter

A free-running time-of-day counter, consisting of seconds and nanoseconds register fields, can be initialized and periodically adjusted (via drift/offset adjustment registers) by system software implementing the PTP servo/clock-synchronization algorithm, providing the time base against which transmit and receive timestamps are referenced.

### 5.2. PCS Configuration Register Space

> **Note:** In MAC and PCS variations, the PCS registers occupy the MAC register space and are accessed via the MAC's 32-bit Avalon-MM control interface. ### 5.3. Register Initialization

The Triple-Speed Ethernet IP core supports various interfaces commonly used by Ethernet solutions: MII/GMII, RGMII, 10-bit Interface, SGMII, 1000BASE-X, and MDIO (for external PHY register configuration). When using the IP core with an external interface, you must understand the requirements and initialize the registers.

Register initialization is mainly performed in the following configurations:
- External PHY Initialization using MDIO (optional)
- PCS Configuration Register Initialization
- MAC Configuration Register Initialization

This section discusses register initialization for the following example Ethernet systems:
- Triple-Speed Ethernet System with MII/GMII or RGMII
- Triple-Speed Ethernet System with SGMII
- Triple-Speed Ethernet System with 1000BASE-X Interface

#### 5.3.1. Triple-Speed Ethernet System with MII/GMII or RGMII

*Figure 39. Triple-Speed Ethernet System with MII/GMII or RGMII with Register Initialization Recommendation* — a 10/100/1000 Mbps MAC connects via Avalon-ST TX/RX and Avalon-MM to a host, and via MII/GMII/RGMII plus MDIO to an external PHY (whose register space is accessed by mapping the PHY's MDIO slave registers into MDIO Space 0), which in turn connects to the copper/fiber interface.

Recommended initialization sequence:

1. **External PHY Initialization using MDIO**
   ```
   // Assume the external PHY address is 0x0A
   mdio_addr0 = 0x0A
   // External PHY registers now map to MDIO Space 0
   // Read/write MDIO Space 0 (dword offset 0x80-0x9F) = Read/write PHY Register 0 to 31
   ```
2. **MAC Configuration Register Initialization**
   1. *Disable MAC transmit and receive datapath* before changing configuration:
      ```
      // Set TX_ENA and RX_ENA bit to 0 in Command Config Register
      command_config = 0x00802220
      // Read back to confirm TX_ENA/RX_ENA are 0 (TX/RX path disabled)
      wait command_config == 0x00802220
      ```
   2. *MAC FIFO configuration:*
      ```
      tx_section_empty = Max FIFO size - 16
      tx_almost_full   = 3
      tx_almost_empty  = 8
      rx_section_empty = Max FIFO size - 16
      rx_almost_full   = 8
      rx_almost_empty  = 8
      // Cut-through mode; set this threshold to 0 to enable store-and-forward mode
      tx_section_full  = 16
      // Cut-through mode; set this threshold to 0 to enable store-and-forward mode
      rx_section_full  = 16
      ```
   3. *MAC address configuration:*
      ```
      // MAC address is 00-1C-23-17-4A-CB
      mac_0 = 0x17231C00
      mac_1 = 0x0000CB4A
      ```
   4. *MAC function configuration:*
      ```
      // Maximum frame length is 1518 bytes
      frm_length = 1518
      // Minimum interpacket gap is 12 bytes
      tx_ipg_length = 12
      // Maximum pause quanta value for flow control
      pause_quant = 0xFFFF
      // Set the MAC with: 100 Mbps and full duplex (obtained from PHY/PCS status),
      // padding removal on receive, CRC removal, TX MAC address insertion using mac_0/mac_1
      command_config = 0x00800220
      ```
   5. *Reset MAC* — Intel recommends a software reset whenever the MAC speed or duplex changes; the software reset bit self-clears when complete:
      ```
      // Set SW_RESET bit to 1
      command_config = 0x00802220
      wait command_config == 0x00800220
      ```
   6. *Enable MAC transmit and receive datapath:*
      ```
      // Set TX_ENA and RX_ENA to 1 in Command Config Register
      command_config = 0x00800223
      // Read back to confirm TX_ENA/RX_ENA are 1 (TX/RX path enabled)
      wait command_config == 0x00800223
      ```

## 7. Design Considerations

This chapter describes guidelines and considerations for integrating the Triple-Speed Ethernet IP core into your system.

### 7.1. Clock Domain Considerations

Carefully plan the clock domains in your system, especially when the Avalon-ST client clock, the MII/GMII/RGMII network clocks, and the PCS/PMA reference clock are not derived from a common source. Where clock domains are asynchronous, use the corresponding independent reset signals described in [Clock and Reset Interface Signals](#61-clock-and-reset-interface-signals) so that each domain can be reset cleanly without introducing metastability into the others.

### 7.2. IP Payload Re-alignment

Some system architectures require that frame payloads delivered to, or received from, the client logic be aligned on a 32-bit boundary within the frame (for example, to simplify downstream processing of IP/TCP headers). Turning on the **Align packet headers to 32-bit boundaries** option, together with the `TX_SHIFT16` and `RX_SHIFT16` bits in the `tx_cmd_stat`/`rx_cmd_stat` registers (described in [Transmit and Receive Command Registers](#513-transmit-and-receive-command-registers-dword-offset-0x3a-0x3b)), causes the IP core to insert or remove a 16-bit shift in the datapath so that frame payloads land on a 32-bit-aligned boundary after the Ethernet header.

### 7.3. Flow Control Considerations

When enabling flow control, ensure the FIFO buffer thresholds (`rx_section_full`, `rx_almost_full`, `tx_almost_full`, and related registers) and the `pause_quant`/`holdoff_quant` values are chosen consistently with your system's latency and buffering budget, so that pause frames are generated with sufficient lead time to prevent FIFO overflow at the configured link speed.

### 7.4. Multi-Port MAC Considerations

In multi-port MAC variations, remember that several base configuration registers (`rev`, `scratch`, `frm_length`, `pause_quant`, `mdio_addr0`/`mdio_addr1`, `tx_ipg_length`) are shared across all port instances and physically reside only in the register space of the first port; writing them through the register space of any other port has no effect.

### 7.5. Resetting the IP Core

Use a hardware reset after power-up and whenever clock domains are re-established. Use a software reset (the `SW_RESET` bit in `command_config`, or the PCS control register's `RESET` bit) when you need to reconfigure the MAC or PCS without disturbing the surrounding system-level reset tree — for example, whenever the negotiated link speed or duplex mode changes, as described in [Register Initialization](#53-register-initialization).

### 7.6. Guideline for SGMII/1000BASE-X Designs

When using the embedded PMA (transceiver-based or LVDS-based), follow the device family's transceiver/LVDS SERDES design guidelines for reference clock selection, PLL cascading, and dynamic reconfiguration, and ensure the `reconfig_to_xcvr`/`reconfig_from_xcvr` buses are correctly shared if multiple IP core instances share PLL resources (see [Instantiating Multiple Instances of Triple-Speed Ethernet IP Cores](#25-instantiating-multiple-instances-of-triple-speed-ethernet-ip-cores)).

## 9. Testbench

Intel provides a parameterizable testbench and a set of example design files with the Triple-Speed Ethernet IP core (available through the IP core's example design generation flow and the Triple-Speed Ethernet Design Examples available in the Intel FPGA Design Store) to help you verify your system-level integration of the IP core.

### 9.1. Testbench Architecture

The testbench instantiates the generated IP core variation together with a configurable Avalon-ST frame generator/checker (BFM) on the client side and, depending on the variation, either a loopback model or a BFM/behavioral model of an external PHY on the network side. - MDIO master read/write access to a behavioral PHY model.
- Frame transmission and reception, including error handling (CRC error injection/detection, undersized/oversized frames).
- Address filtering (primary/supplementary unicast addresses, multicast hash table, promiscuous mode, broadcast).

## 10. Software Programming Interface

This chapter describes the software programming model for the Triple-Speed Ethernet IP core's Avalon-MM configuration and status register space, intended for system software (for example, a Nios II or HPS driver) that configures and monitors the IP core at run time.

### 10.1. Register Access Overview

All configuration, status, and statistics registers described in [Configuration Register Space](#5-configuration-register-space) are accessed as 32-bit dwords through the Avalon-MM control interface (see [Avalon-MM Configuration and Status Interface Signals](#64-avalon-mm-configuration-and-status-interface-signals)). Software typically performs the following steps at initialization: configure FIFO thresholds and the primary MAC address, configure `command_config` (deferring `TX_ENA`/`RX_ENA` to last), and, for PCS-containing variations, configure the `if_mode`, `link_timer`, and `control` registers before enabling auto-negotiation. See [Register Initialization](#53-register-initialization) for complete worked examples for MII/GMII/RGMII, SGMII, and 1000BASE-X systems.

### 10.2. MDIO Driver Considerations

When the MDIO master is enabled, software accesses an external PHY's management registers indirectly through MDIO Space 0/1 (dword offsets 0x80–0x9F/0xA0–0xBF). Because each MDIO access initiates a serial MDC/MDIO transaction with the PHY, software should expect a multi-cycle latency per access (the Avalon-MM `cfg_waitrequest` signal, or a documented polling bit, indicates when a transaction has completed) and should not assume single-cycle completion as with the other Avalon-MM registers.

### 10.3. Statistics Counter Handling

Because the statistics counters (see [Statistics Counters](#512-statistics-counters-dword-offset-0x18-0x38)) roll over when full, software that needs cumulative long-term counts should poll the counters periodically (more frequently than the expected overflow interval at the configured link rate) and accumulate the deltas into wider software-maintained counters, or enable the 64-bit extended statistics counters option where available.

### 10.4. IEEE 1588v2 Software Considerations

Software implementing the PTP servo algorithm reads the transmit/receive timestamp registers tagged to specific PTP event frames (see [IEEE 1588v2 Feature](#47-ieee-1588v2-feature) and [IEEE 1588v2 Feature (Dword Offset 0xD0 – 0xD6)](#515-ieee-1588v2-feature-dword-offset-0xd0-0xd6)), applies the fixed PMA/datapath delay compensation documented in [IEEE 1588v2 Feature PMA Delay](#516-ieee-1588v2-feature-pma-delay), and periodically updates the `tx_period`/`rx_period` and `tx_adjust_ns`/`rx_adjust_ns`/`tx_adjust_fns`/`rx_adjust_fns` registers to discipline the local time-of-day counter to the PTP grandmaster.

| Length/Type | 2 | As in the basic frame. |
| Payload | up to the configured maximum (jumbo frames up to 64 Kbytes in MAC-only variants, or up to 10 Kbytes in variants with the 1000BASE-X/SGMII PCS) | — |
| FCS | 4 | As in the basic frame. |

| Field | Size (bytes) | Description |
|---|---|---|
